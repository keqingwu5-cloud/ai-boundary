# 第一大腦｜GitHub 發布前置條件閘門 V0.1（審閱及安裝候選）

> 本文件僅為獨立草稿分支上的候選設計。**目前未安裝到正式 main、未啟用強制保護、未部署、未改權限或自動發布任務。**

## 目的
在使用者或 BOT 建立新問題、新方案、修補及發布計畫時，**先要求說明適用前提，再確認方案**。重用全域條件式機制，記錄原始前因及新後果，不讓新結果覆蓋原始問題。減少因遺漏身分、來源、授權與歷史依賴而重複修改。

## 適用時機與邊界
- **方案提出時**：生成條件申報，檢查舊問題、既有機制及必要資料；允許草稿、諮詢、純讀取與隔離候選，不代表可以發布。
- **提交 PR 前**：再驗證資料契約、授權、修改範圍、測試及證據清單。
- **推送或部署前**：對受保護操作強制拒絕缺少必要條件的變更，不能以文字聲稱「已驗證」取代可信憑證。
- **發布後**：以追加事件保留前因、commit、CI、驗收結果、例外與回滾資訊，不覆蓋歷史。
- 任何相同能力的節點可重用同一個機制；只有滿足該機制定義的啟用條件才啟用。條件不適用應留下理由。

## 前置申報欄位
| 欄位 | 要求 |
|---|---|
| proposal_id/problem_id | 永久識別及原始問題連結 |
| intent / 原始前因 | 為何提出、預期後果、相關歷史 Issue/PR |
| actor / receiver | 提出者、執行者、預期目的端及可靠身分驗證來源 |
| source | 原始資料／程式／外部來源 ID、網址、版本與可信度 |
| content_digest / policy_version | 資料內容雜湊、當時生效的政策版本及驗證方式 |
| permissions / approver | 操作類別、必要授權者、授權範圍、證據及有效期限 |
| applicable_mechanisms | 可以重用的既有機制、啟用前提與排除條件 |
| dependencies | 涉及模組、上下游、潛在衝突、舊問題及回歸測試 |
| required_evidence | commit SHA、CI、隔離測試、獨立 ACK（適用時）、時間 |
| rollback_and_failure | 操作不可逆性、失敗與恢復方式 |

## 判定規則
- `READY_FOR_REVIEW`：有足夠背景可以審閱，不表示可發布。
- `NEEDS_INFO`：缺失條件需標明「為何需要、誰能提供、未提供的影響」。
- `CANDIDATE_ONLY`：允許無正式資料存取的隔離測試或草稿工作。
- `AUTHORIZED_FOR_SCOPE`：所有必要條件、授權及範圍皆有可核驗證據。
- `DENIED`：受保護操作的身份、來源、授權或政策不符合，必須 fail-closed。
- `NOT_APPLICABLE`：有可稽核的排除理由，不能跳過所有安全檢查。

## 既有發布路徑
已核對 `scripts/publish_episode.sh`：目前腳本在影片轉檔與 `data.js` 更新後執行 commit，且預設 push `origin HEAD:main`。**若要實作閘門，應在任何修改正式檔案、commit 或 push 前就先做 preflight；並在 publish 前再次檢查。**
切勿僅限制此腳本：其他直接 push、PR merge、GitHub Pages、API 執行者仍可能繞過。真正強制性需要經核准後配置所有發布路徑的保護／CI／權限，現階段僅提出設計，不擅改權限。

## 最小隔離測試
1. 缺少簽認來源、身分、必要授權時，受保護發布 fail-closed；審閱草稿仍可保存。
2. 不適用的條件保留明確理由；高風險安全條件不得藉由不適用而繞過。
3. 相同原始前因加上新結果不覆蓋原紀錄；只追加狀態與可回讀證據。
4. 既有機制的同義關鍵字與相同問題 ID 可重用；不因相同文字就合併兩個獨立任務。
5. 變更來源、接收者、資料內容雜湊、授權範圍或政策版本後，原核准失效並重新審查。
6. 確認 `--no-push` 或隔離分支不意外觸及 main，且缺失條件時不更改正式資料。
7. GPT② 真實接收／ACK 與合成 CI 要分層報告，真實跨 AI E2E 保留為最後驗收。

## 雙方審閱
- GPT①：檢查本文件與原始需求、歷史問題關聯、使用者確認介面、權限及適用條件。
- GPT②：檢查現有發布程式、分支／CI／資料契約，指出如何最小化接入，不重建已存在的能力。
- 審閱輸出：已存在、需補充、衝突、測試及授權要求，各附固定來源。
