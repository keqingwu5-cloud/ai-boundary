# TCVL｜AI 負責人制度與資料室原檔治理 V0.1

> 需求來源：每個 AI 必須有對應人員與資料整理責任；每位 AI 的整理、拒絕與修正結果需上交；原始資料交由資料室治理，不因摘要、審查、修正而被覆寫。

## 操作方式與責任流向

**人工建立專案任務 → 為 GPT①、GPT②、BOT③ 分別指定負責人、資料整理職責及人工審核者 → 登記原始檔 ID／版本／保管人／索引 → 按角色登記整理稿 → 人工審核、否決或要求修正 → 產生待審記憶候選 → 經加密記憶庫人工審核。**

三方人員分工不等於三方獨立模型已自動完成任務，初始負責人不會自動填入虛構的人名。

| 角色 | 責任 | 應上交內容 |
|---|---|---|
| GPT① 統籌 | 問題定義、研究整合、任務分配與解法候選 | 目標、研究摘要、來源 ID、假設、缺口、交接 |
| GPT② 反證 | 獨立審查、異議、替代解釋、風險 | 原主張 ID、反證、拒絕／異議、影響、退回 |
| BOT③ 測試 | 條件、可重現性、邊界與反例測試 | 測試案例、資料依據、測試結果、失敗限制與重測 |

每一 AI 的界面顯示「人類負責人代號」「資料整理與上交責任」「人工審核者代號」「原指令 ID」「上交數量／審查狀態」，不得將使用者人工貼回的摘要冒充遠端 AI 身分驗證。

## 原檔、整理稿與審查分離

**原始檔治理索引**保留：原始 ID、原始標題、私人資料室代號、原檔保管者、版本、日期、可選 SHA-256（使用者提供而未獨立驗證）。相同原檔 ID 不能再次登記覆蓋，應建立新版本／新 ID。

**整理稿上交**保留：上交 ID、對應 AI 角色、負責人、來源聲稱、原檔 ID、摘要、證據、異議／未知、下一步與時間。作者身份固定為「尚未驗證」直到未來設置可信回執。

**人工審核**保留：同一上交 ID 的每次審核決定、人工審查人、理由、影響與下一步，拒絕不得刪除原始上交或原檔索引。

### 現階段安全界線

- 這是**純前端的資料室引用索引**，沒有上傳、儲存或託管真正的原始檔案。主腦專案目前沒有私人檔案伺服器。輸入原檔索引**不是**原檔本體已保存的證明。
- 原始檔需由使用者另外保存在自己控制的私人或加密儲存。待未來有後端、權限、加密、版本／雜湊驗證及恢復流程後才能稱為真正的資料室檔案保管。
- 人工操作紀錄暫存在當前頁面，離開前要分別匯出 **三方批次 JSON** 與 **資料室治理索引 JSON**。兩者以同一專案 ID／批次 ID 對應；匯入錯誤批次會拒絕。
- **下載的治理索引 JSON 未加密**。只用人員代號及私人資料室引用代碼，不要加入密碼、機密 API 金鑰、真實私人路徑或機密原文；檔案不可提交到公開 GitHub 儲存庫。
- 審核者可以「同意歸檔」，但這仍只是**人工處置狀態**，不等於原始檔真的已由平台託管、證據真實，或正式記憶已核准。
- 原檔本體不進入記憶候選包；只保留索引、整理內容、來源及審核紀錄。從加密記憶頁匯入仍須人工核准。

## 平台路徑與目前完成度

- `relay-hub.html#dataRoomCenter`：三方 AI 對應人員、原始資料索引、整理上交、人工審查、拒絕與歷史。
- `architecture-hub.html#dataRoomLane`：架構圖中的橫向資料室治理功能說明與入口。
- `tcvl-platform-shell.js`：全平台共用「資料室治理」導航入口。
- `tcvl-data-room-core.js`：獨立資料驗證、不可覆蓋原始索引、角色指派、上交、審查與待審記憶包。
- `tests/tcvl-data-room-core.test.cjs`：17 項責任、來源、審查與不可覆蓋驗證案例。
