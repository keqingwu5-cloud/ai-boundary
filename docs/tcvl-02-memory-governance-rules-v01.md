# 文件 ②｜主腦規章制度與長期記憶治理 V0.1

**文件定位：共同遵守的規章。** 本文件回答「為了讓主腦未來的記憶持續可靠，什麼能留、什麼要審、什麼不能被覆寫」。它不是平台功能清單，也不是個別拒絕事件的操作手冊。

- 目前狀態：**待審規章草案**；尚未直接成為程式強制規則。
- 適用：使用者、主腦協作入口、GPT①、GPT②、BOT③、計畫觀察員、資料導入及任何未來外部接口。
- 生效條件：由使用者核准規章版次、適用專案及生效時間；重要變更必須保留舊版。
- 對應文件：① 規劃方向 `tcvl-01-planning-direction-v01.md`；③ 拒絕修正 `tcvl-03-rejection-correction-observer-v01.md`。

## 第一章｜治理目的與底線

規章的目的**不是阻止 AI 工作**，而是讓未來的 AI 能從真實情況、分歧、錯誤、退回及修正中取得可靠的歷史，避免把同一個錯誤重新包裝成新答案。

**第一條｜不能把敘事當事實。** 系統必須區分「原始資料」「主張／推測」「支持或反對證據」「測試結果」「人的決策」「仍未確認之處」。三個 AI 意見一致，也不能取代外部事實。

**第二條｜記錄不能以新蓋舊。** 原始版本、否決理由、已存在的反證、修正版、時間與執行者都要保留可追溯引用。更改只能新增版本、審查事件或連結；刪除／到期／隱私例外另需合法與授權處理，不等於永久保留所有私人內容。

**第三條｜不知道就記錄不知道。** 不得為了讓流程完成而假填來源、身分、測試結果、接收回執、批准日期與接口連線狀態。

**第四條｜權限與驗證分離。** 能提出候選不等於能修改正式記憶；能記錄「收到結果」不等於結果通過驗證；能提交修正者不能單獨核准自己的重大變更。

**第五條｜停止工作不停止對話。** 「暫停指定工作」不等於刪掉任務、清空記憶、封鎖所有聊天。停下的工作必須保留當時狀態與恢復條件。

## 第二章｜專案與任務識別規範

每個**正式執行任務**都應有核准的專案計畫（允許極短的簡化計畫，但不允許跳過前置對齊）；至少保留：

| 必填項目 | 目的 |
|---|---|
| `project_id`、`task_id`、`plan_id`／`plan_version` | 找回這次工作所依據的確切計畫 |
| 目標、完成定義、禁止行動、適用邊界 | 判斷偏離是什麼 |
| 負責人與觀察員角色、授權範圍 | 誰做事、誰監督、誰有權核准 |
| 參考證據與記憶版次 | 避免混入事後才知道的答案 |
| 預期輸入、輸出、期限／檢查點 | 說明任務如何完成 |
| 風險、停止條件、回復路徑 | 出錯時能保住進度並退回 |
| 前／中／後對齊結果及簽核 | 確定依計畫進行，還是需要變更 |

不同對話窗可以連到同一個 `project_id`，但只有經權限允許的專案摘要、已批准決策與必要記憶能帶到新對話。

## 第三章｜全平台共通狀態的制度

共用的是**狀態字典及遷移規則**，不是把所有類型都塞進同一欄：

| 對象 | 建議狀態 |
|---|---|
| 工作任務 | 候選、待前置審查、准予開始、執行中、等待補證、暫停、被拒絕、待後置驗收、完成、取消、待重審 |
| 計畫版次 | 草稿、待審、已核准、生效中、已修訂／被取代、暫停生效 |
| 記憶候選 | 待核查、衝突、待補充、被拒絕、待核准、已核准、已被取代 |
| 模組建設 | 規劃中、建置中、待整體驗收、已驗收、待重審 |
| 接口連線 | 未規劃、尚未接通、人工交接、示範模式、測試中、已驗證連線、異常、停用 |
| 觀察員門檻 | 尚未對齊、符合、偏離、證據不足、待人工決策 |

**重要：**「已完成任務」不代表「已核准記憶」，「節點驗證通過」不代表「接口已連線」，「已分享指令」不代表「對方已收到」。每次狀態變化須保留舊狀態、變更原因、執行者、資料版次及時間。

使用者可以提出新增狀態選項，但新選項需說明**適用對象、語意、允許的前後狀態及既有紀錄的相容性**，經規章審查才能納入全平台字典。未知狀態不應被自動當作完成。

## 第四章｜記憶分類、版本與否決保留

分層記憶採用既有主腦的概念架構：

1. **L0 原始候選**：保留原文、來源聲稱、未驗證項及可能拒絕的資料。
2. **L1 資料進出與來源事件**：從哪裡來、實際何時收到、版本與可用權限。
3. **L2 主張與問題模型**：假設、研究目標及相互競爭的解釋。
4. **L3 反證與測試**：反對意見、實測條件、失效邊界、結果與限制。
5. **L4 決策與修復沿革**：誰批准、誰拒絕、原因、回退、影響及對應新版本。
6. **L5 已核准的正式知識**：具明確適用範圍、來源與版本的可用內容。

這六層是**治理邏輯層**，不強迫建立六個互不相容的實體資料庫。拒絕紀錄可以重新研究，但必須引用原拒絕 ID、理由、仍然有效的反證、改變的條件及新證據，不能複製成「全新已核准主張」。

### 最小事件規格

`event_id`、`project_id`、`task_id`（適用時）、`record_id`、`record_version`、`event_kind`、`claimed_actor`、`verified_identity_status`、`occurred_at`、`recorded_at`、`source_links`、`old_status`、`new_status`、`reason`、`evidence_refs`、`impact_refs`、`next_action`、`approval_refs`。

**時間隔離：**在回溯過去某時點時，只能使用當時已存在、且當時已進入系統的記錄。發生時間和記錄時間需分開。

## 第五章｜計畫觀察員的制度位置

計畫觀察員可先是**平台檢查程序／固定職責**，不必立刻引入第四個大型模型；也可由獨立審查者協助，但必須記錄是否真正獨立。

- **事前強制對齊**：核對計畫版次、目的、角色、允許操作、交付物、停止條件；未符合不能把任務標為「准予開始」。
- **過程強制對齊**：每個明確里程碑和重大變更前，檢查目前工作是否還符合原版目標；偏離時要求事件記錄、影響判斷和重新審批。
- **事後強制對齊**：確認結果是否對應目的、證據及交付標準；若不符合，要標記拒絕、待補證或返工，而非強迫完成。
- **權限分離**：觀察員只能提出「符合／不符／不足以判斷」、要求補證、建議暫停及通知使用者；**不得自行改寫核准計畫或直接批准正式記憶**。
- **提前審查**：使用者可在工作開始前指定必須回答的問題、不可突破的範圍及檢查頻率；高風險修改需使用者顯式核准。

觀察員可以發現流程問題，不能保證研究結論的事實真實性；外部接收、測試與完成狀態需另外取得可驗證依據。

## 第六章｜規章修改、例外與稽核

修改本規章必須保留：`policy_version`、變更理由、差異、提出者、評估影響、尚存反對意見、核准人與生效時點。任何在進行中的專案，使用的規章版次應維持明確；要切換版本，須以變更事件說明，不能偷偷換規則造成前後不可比較。

**緊急暫停例外：**當有安全、資料外洩或重複寫入風險時，允許先行禁止新的高風險執行，但要立即記錄原因與影響；不許以緊急事件為藉口刪除證據。

**保密與可視化：**公開圖可顯示匿名節點與統計；實際私人記憶需在已授權、解鎖的環境查看。可隱藏畫面不等於刪除歷史。對外影片可以只展示效果，但示範必須標示為示範。

## 第七章｜本規章的驗收方式

規章版次只有經使用者審查、測試規則具備可檢查的實作對應，才能標示「已採用」。可透過下列問題判斷是否完善：

- 過去被拒絕的方案能否查到**原版 + 原因 + 仍有效反證**？
- 每次 AI 任務能否找回其**核准計畫版次及前／中／後對齊**？
- 新對話是否知道專案目標，但不洩漏其他專案資料？
- 任務暫停後是否保留進度、仍能對話、且重新啟動需要審批？
- 觀察員與執行者、正式核准者的權限是否真正分開？
- 新的狀態選項能否與既有資料共存，而不是無痕改名舊狀態？

**目前事實界線：**原型已有本機加密記憶、部分人工候選／拒絕／版本管理；本規章中的全平台強制觀察員與統一狀態字典仍是候選制度，不得宣稱已部署。
