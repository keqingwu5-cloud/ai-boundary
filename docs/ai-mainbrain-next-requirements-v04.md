| 路徑擴充 | 延伸節點、分支與依賴，保留既有關聯 | 支援新增節點與分支並保留舊 ID/版本/連線；區分依賴、引用、工作流方向與已證實因果；路徑圖同步顯示每段接口的手動/展示/規劃狀態 |

## 設計與介面共用規則

- 一項任務可以切換狀態、暫停與重新啟動，不應中斷「對話」操作；要區分任務取消與聊天終止。
- 所有通知與拒絕訊息應有**及時介面提醒**（目前頁面內），但沒有外部推送或遠端訂閱時不得聲稱跨分頁、跨裝置即時通知。
- 節點、接口、任務、模組狀態應各自有明確定義與轉移條件，不可讓單一節點通過就把整個模組標記完成。詳細參見治理文件內「節點已驗證 ≠ 模組已完成」。
- 圖像與版圖是第一層資訊；點選才展開「用途 → 輸入 → 處理 → 輸出 → 接口 → 拒絕/修正 → 歷史」，最後才選擇看技術細節。
- 雙向紀錄可以顯示/隱藏，但不能因此刪掉原始資料；正式記憶繼續使用現有本機加密與人工候選審核，不從 GitHub Pages 公開頁直接讀寫個人記憶。
- 未來有新的接口時先新增為規劃/虛化節點，授權與驗收過後才能變成可用。

## 整合順序與測試策略

使用者要求「**先補齊同批需求，再集中確認，不額外擴充測試流程**」。解讀為：先做一次架構盤點和整體設計，將同一批功能在隔離分支接通，再集中走端到端驗收，避免每新增一張卡片就要求使用者重新測整站。**不能**跳過安全關鍵單元測試、加密庫不變更保證、既有功能回歸檢查或實際可用性驗收。

推薦最小順序：
1. 盤點現有功能及 API/本機界線，定義共用狀態字典與專案/任務/事件 ID。
2. 在平台導覽與共用狀態層一次加入停止/提醒/設定入口與虛化邏輯（先呈現真實狀態，再接上存在的功能）。
3. 將新需求寫進未來版圖候選區；加強路徑與資料依賴，不覆寫舊記錄。
4. 批次合併本分支的新 UI 工作後做一輪核心測試、一次跨頁互動測試、一次加密記憶回歸/PR #27 相容測試、一次手機實機驗收；測不過再逐項修復與重測。
