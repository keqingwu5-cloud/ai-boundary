# TCVL｜三方 AI 中樞交接節點與通路驗收 V0.1

> 狀態：**開發分支上的手動交接節點**。沒有 GPT①、GPT②、BOT③ 的真實 API、自動認證或遠端停止能力，不能以單元測試代替「三個 AI 已真正收到」。

## 使用者要解決的問題

目前主腦、發射器、專案治理、回溯與記憶審核是不同的入口。這輪要建立一個可理解、可操作的「**這段對話人工交接 → 三方 AI 指令 → 個別回報 → 主腦專案治理 → 記憶候選審核**」節點。

## 平台操作路徑

1. 在 `governance-board.html` 建立專案和對話，複製顯示的**專案 ID**。該工作區只有本頁暫存，離開前要自行匯出 JSON。
2. 從 `mainbrain.html#relay` 或 `relay-hub.html` 進入三方中樞交接；輸入同一專案 ID、目標、背景、完成條件和停止條件。
3. 建立批次後產生三個不同的原指令 ID：`批次:GPT1`、`批次:GPT2`、`批次:BOT3`。三方工作職責分開，不能讓一個 AI 的人工回覆冒充另一個角色。
4. 點每個角色的「發射＝複製指令」並**手動貼給外部 AI**，或先「下載指令 JSON」，再在 `launcher.html` 用「匯入三方中樞原指令 JSON」載入，保留完全相同的 command ID。此流程不是真正的遠端自動送達。
5. 回覆可在交接節點手動貼上，或先從 Launcher「下載回報 JSON」再由交接節點的「匯入相同原指令回報」讀入；兩條路徑都必須核對原指令 ID 和角色。來源**仍未通過真實身分驗證**。
6. 任一角色若拒絕，當下填上原因、影響範圍、下一步；拒絕不會覆寫已保留的原回報。停止功能只停止該角色的**本機工作追蹤**，對話可以繼續。
7. 交接節點匯出 `tcvl.relay-transfer.v0.1`，到專案治理中同一個 Project ID、同一個對話使用「匯入三方交接回報（人工）」，明確確認後追加回報；拒絕會觸發原因、影響與下一步通知。匯入是原資料的人工記錄，不是知識核准。
8. 需要進入正式記憶候選時，交接節點可以匯出 `ai-boundary.memory-pack.v1`，在 `memory.html` **解鎖、人工匯入並審核**，不能跳過既有審核程序。

## 逐段狀態與設計邊界

| 通路 | 平台目前能檢查什麼 | 不能宣稱什麼 |
|---|---|---|
| 專案 → 中樞 | 手動核對 Project ID、任務目的 | 自動取得本 ChatGPT 對話全文 |
| 中樞 → 三方 | 三份獨立原指令、內容與角色 | 三個 AI 已真正接收 |
| 中樞 → Launcher | 原指令格式、角色與 command ID | Launcher 會替使用者調用遠端 API |
| Launcher → 中樞 | 回報結構、原指令 ID、角色 | 回報者身分已被證實 |
| 中樞 → 專案 | JSON 格式、對話歸屬、重複匯入、拒絕提醒 | 回報已通過事實驗證 |
| 專案 → 記憶 | 候選包格式與人工審批 | 無條件自動寫入權威記憶 |
| 停止 → 繼續 | 保留每個角色的本機狀態和歷史 | 已撤銷遠端 AI 正在執行的任務 |

所有資料均保留未驗證身分標記。資料庫不應把「已複製」換成「已送達」，也不應把「三份回報齊全」當成真實共識。

## 已設定的異常案例

- 錯誤角色的回報不可掛在另一個原指令 ID。
- 重複回報 ID、重複交接批次匯入必須拒絕。
- 停止某角色不應影響其他兩位、也不妨礙專案對話繼續。
- 缺少拒絕理由、影響、下一步，不能登記拒絕。
- 來源聲稱或回報簽名不等於經身份證實。
- 匯入到錯誤 Project ID 必須拒絕，不能自行建立或覆寫既有專案。
- 過長回報不可以悄悄截斷；符合上限時以數段保留完整資料。
- 一個角色拒絕不代表全部角色失敗；正式核准永遠需人工審查。
