# 文件 ③｜拒絕條件、修正方向與計畫觀察員 V0.1

**文件定位：專案執行前／中／後的具體操作規格。** 本文件回答「何時應拒絕、停止哪個工作、退回誰、如何補證、怎麼重新開始」，並把使用者的**提前審查模式**設為每個正式任務的入口。

- 狀態：**待審規格**，尚未成為線上自動觀察員或真實 AI 指令調度器。
- 依據：文件 ① `tcvl-01-planning-direction-v01.md` 定義產品與平台方向；文件 ② `tcvl-02-memory-governance-rules-v01.md` 定義權限、記憶與共同狀態。本文件不改動文件 ② 的治理底線。
- 核心原則：**先對齊再作業；中途偏離立即標記；結束要回到原計畫比對**。

## 1. 「計畫觀察員」是什麼？

每個專案建立時，一起建立一份**計畫基準（Plan Baseline）**，觀察員只負責反覆拿**執行現況**和**當前已核准計畫**比較。

它不負責代替 GPT① 提出結論、代替 GPT② 找反證，或代替 BOT③ 執行實驗；也**不擔任最終審批者**。初期可由規則表單和人工覆核實現，未來才研究是否使用獨立 AI 觀察員。

使用者要能在計畫尚未開始前問它：「**這個目標、工作方式和路徑有哪些未補足？誰可能偏離？何時該停止？**」這就是**預審**，不是等到事後出現拒絕才詢問。

### 必填的專案基準

| 欄位 | 具體意義 |
|---|---|
| `project_id`、`plan_id`、`plan_version` | 對哪一個專案、哪一版計畫負責 |
| `objective`、`success_criteria` | 要完成什麼，怎樣才算符合 |
| `roles`、`permissions` | 誰研究、誰反證、誰執行、誰批准 |
| `data_scope`、`evidence_refs` | 可用資料和引用邊界 |
| `task_steps`、`checkpoints` | 哪些階段需回報與對齊 |
| `stop_conditions` | 什麼情況下要求停止指定工作 |
| `rejection_policy_version` | 本任務採用哪一版拒絕條件 |
| `approved_by`、`approved_at` | 人工是否允許開始 |
| `revision_history` | 後續為何更改計畫，舊版在何處 |

觀察員不得替沒有資料的欄位編造預設的「已通過」內容。可以記「尚未知」，但有必要欄位尚缺或風險未核准時不得進入正式執行。

## 2. 三道強制對齊門檻

### G0｜開始前：計畫審查

**觸發：** 新建專案、新任務、改變執行角色、擴張資料權限、擬用新的 AI 或外部接口。

觀察員依序檢查：

- 問題與目標是否具體、是否與計畫版本相符？
- 工作路線、交付物、負責人、資料來源及反證路徑是否明確？
- 是否已指定 GPT①、GPT②、BOT③ 的獨立責任與完成定義？
- 權限、風險、保密、停止條件是否清楚？
- 有無被拒絕的舊方案或仍未解除的反證？這次為何可以重新研究？
- 使用者是否完成預審、允許本任務按這一版本開始？

**結論：** `aligned`（符合、待授權啟動）、`needs_information`（缺資料）、`deviation`（與計畫衝突）。只有經人工核准後才能標記「准予開始」；不能因為觀察員看到格式完整就逕行啟動外部系統。

### G1｜執行中：持續對齊

**觸發：** 預先設定的每個重要檢查點、提交新證據、拒絕事件、修改路徑、擬使用新接口、超出資料範圍、達到停止條件。

觀察員檢查**已完成的步驟與證據**、**目前行動是否仍然符合目標**、**後續動作是否超出權限或改變原本問題**。

| 結果 | 如何處理 |
|---|---|
| 按計畫 | 記錄 `checkpoint_id`、進度、證據，繼續 |
| 輕微差異、不改目標與授權 | 記錄差異；在下一檢查點再評估 |
| 改變目標、資料權限或評估標準 | **停止受影響的工作分支**，建立新版計畫候選，送使用者事先審查 |
| 證據不足／反證仍有效 | 列為待補證或待反證測試，不強行生成結論 |
| 發生重大安全或資料完整性問題 | 優先暫停相關執行；保留現況、時間、影響範圍並即時提示 |

**停止鍵的準確語意：** 發出 `pause_requested` 或 `cancel_requested`，保存原計畫版次、目前進度、最後已確認回執與待完成事項。**對話可繼續**，使用者可問原因、調整計畫與建立新的審核候選。除非執行端真正回覆停止成功，不能顯示「遠端已停止」。

### G2｜完成後：驗收與記憶候選

觀察員確認交付物對應的**原始目標、核准的後續變更、每個測試的證據、未完成或偏離項**；報告可分類：

- `delivered_as_planned`：流程對齊，交付物符合形式上的完成條件，仍要檢查事實真偽。
- `delivered_with_exception`：偏離已被明確核准並留存新版次。
- `needs_rework`：欠缺條件、資料或反證檢查，需要返工。
- `blocked`：存在未解除拒絕／安全或權限問題。
- `undetermined`：證據不足，不能認定成功／失敗。

**任務完成 ≠ 三方一致 ≠ 記憶核准。** 驗收過後，研究內容才能作為帶來源的記憶候選送至本機審核。

## 3. 修改拒絕條件：先分類，再做決定

拒絕不能只有「不同意」或「失敗」兩個字。每次應先判斷拒絕是什麼性質：

| 類型 | 是否阻止工作 | 主動顯示的修復方向 |
|---|---|---|
| `scope_mismatch` 目的／問題不一致 | 暫停受影響的執行分支 | 對齊原始問題或建立新計畫 |
| `source_unverified` 來源／身分不明 | 阻止提升為已驗證資料 | 補充原始來源及驗證紀錄 |
| `evidence_insufficient` 缺少證據 | 保留待驗證，不自動當作錯誤 | 定義缺什麼、由誰補證 |
| `counterevidence_open` 反證未處理 | 阻止無條件宣稱成立 | 確認反證仍適用的條件並重測 |
| `test_invalid` 測試方式／環境無效 | 停止以此結果作驗收 | 修正實驗設計；不直接說主張錯誤 |
| `permission_violation` 超出權限 | 立即暫停相關操作 | 說明權限差異並申請人工核准 |
| `version_conflict` 版本或資料完整性衝突 | 阻止覆寫與錯誤合併 | 備份、比較版本、保留分支 |
| `plan_deviation` 執行偏離核准計畫 | 停止受影響分支並進入 G0 重審 | 建立變更單、說明影響及新路徑 |
| `resource_limit` 成本／時間上限觸發 | 暫停相應工作 | 估算剩餘成本、縮小範圍或調整計畫 |
| `cannot_determine` 目前無法判定 | 不宣稱通過或拒絕主張 | 明確列出未知及必要條件 |

**拒絕「這次提交」與否認「整個研究方向」必須分開。** 修改拒絕條件需走文件 ② 的規章版次流程，並評估是否影響舊事件與進行中的任務，不可事後偷偷用新規則重新判定以前的資料。

## 4. 拒絕當下必須主動提示，不等使用者再問

每次系統真的產生拒絕／偏離事件時，頁面應顯示：

> **任務 T-001：本次提交已退回（示意）**  
> 對照計畫：P-001 v2，G1 執行中檢查點。  
> 原因：引用來源無法核對；不是已證明原結論錯誤。  
> 影響：此回報不能進入正式記憶，依賴的 M-003 需要重新審查。  
> 建議下一步：補來源 → GPT② 確認反證 → BOT③ 重新測試。  
> 狀態：受影響分支待補證；其他對話可以繼續。  
> 可操作：查看原因、查看依賴路徑、提出修正、要求暫停、送交人工審批。

最低通知欄位：`event_id`、`task_id`、`plan_version`、`gate`、`reason_code`、`human_explanation`、`evidence_refs`、`affected_nodes`、`suggested_paths`、`action_required`、`timestamp`、`delivery_status`。

通知應在**事件進入系統並完成基本格式檢查時**顯示，且在通知中心持續保留未處理狀態。顯示／隱藏只影響閱讀介面，不得刪除原始拒絕與修正歷史。對尚未連線的 AI，不能偽稱已接收到拒絕提醒。

## 5. 修改、補證、反證、重測的閉環

以下每一輪都必須關聯原始資料與計畫 ID：

`原始執行 → 觀察員指出差異 → 保留拒絕／異常 ID → 影響路徑掃描 → 提出修改候選 → GPT② 審查 → BOT③ 依明確條件重測 → 觀察員重新對齊 → 使用者核准／退回 → 記憶審核`。

**提前審查使用方式：** 在任務開始前，使用者可以把預計研究題目與路線先送觀察員演練。觀察員輸出「最可能偏離目標的位置、缺少的證據、需要的停止條件、建議增加的檢查點」；該演練不能冒稱真的做過後續測試。

如果修正引入新目標、不同資料、不同測試標準，要建立新的 `plan_version` 或獨立分支；修正前後比較時必須寫明是否仍可比較。發生因果爭議，僅先列出引用與依賴，不將關聯誤寫成因果證明。

## 6. 最小「專案觀察卡」示例

| 階段 | 當前問題 | 觀察員要核對的事情 | 結果 |
|---|---|---|---|
| G0 開始前 | 測試模型的新記憶治理方案 | 有否決紀錄與回溯標準？使用者核准了哪一版？ | 未核准不得開始 |
| G1 中途 | GPT② 發現來源不明 | 這個問題影響哪些任務？是否要停止 BOT③ 的相關測試？ | 退回補證、保留原因 |
| G2 完成後 | BOT③ 提交重測報告 | 與原目標、證據邊界、已批准修改是否一致？ | 等待人工驗收 |

觀察員**對齊的是計畫與流程**；測試主張是否真實還需要 GPT②、BOT③ 和獨立證據。不可用「每輪三個 AI 都一致」代替驗證。

## 7. 介面與項目治理規則

- 每個專案有「核准計畫」「執行進度」「觀察員前中後檢查」「拒絕與修正」「依賴路徑」「未來候選」六個閱讀區，預設優先顯示**當下需處理的偏離**。
- 觀察員門檻顯示可用文字：尚未檢查／符合／偏離／證據不足／待人工核准。不得只靠顏色。
- 停止按鈕僅作用於指定 `task_id`／`execution_id`；計畫仍可討論，新對話須能讀到已批准的計畫摘要。
- 未部署的觀察員與外部接口應呈現虛化版塊及明確的「未啟用／未接線」提示。
- 欄位及拒絕代碼可擴充，但修改前先檢查原事件的向後相容性，並保留每個理由碼的語意版本。

## 8. 測試策略與上線門檻

採用使用者希望的「**先將同批規格補齊，再一次集中驗收**」：先完成三份文件、共同狀態、觀察員門檻、拒絕處置與畫面對應，之後統一做情境驗證，避免每提一個節點就做一輪完整整合測試。

但不能省略必要的**資料安全、停止權限、記憶備份相容性、拒絕不誤報及不可覆寫**測試。

最低需要覆蓋的整合案例：

1. G0 資料不足 → 停止正式執行，產生具體補件提示。
2. G0 已核准 → 可以開始任務，正確關聯 `plan_version`。
3. G1 發現目標偏移 → 只暫停相關任務分支，對話仍能繼續，顯示立即拒絕提醒。
4. G1 補證後恢復 → 保留舊版、原拒絕與新核准關聯，未有回執不得標成遠端已停止／恢復。
5. G2 任務形式上已完成但證據不足 → 標為待補證，不能自動寫入正式記憶。
6. 規章版本修改 → 舊任務仍能回到當時適用的規則，不能用新政策無聲改判歷史。
7. 拒絕資料重新使用 → 原拒絕 ID、仍成立反證與重測範圍俱在，才能進入重新審查。
8. 已停用或不存在的接口 → 必須顯示未接線，不能當作真實任務執行成功。

### 實作前的最後界線

這是**監督規格與拒絕邏輯的設計文件**，不是已經運作的自動觀察員。真正上線需要受控工作執行環境、權限驗證、事件保存與使用者審批流程。現有主腦的人工交接／本機加密記憶功能仍然要維持獨立、安全及可回退。
