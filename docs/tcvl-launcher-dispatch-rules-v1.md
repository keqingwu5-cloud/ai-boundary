# Launcher Hub V1｜三方發射與分工執行規章

> 狀態：開發版作業規章 V1.0（待使用者審核）。本階段**只驗收任務建立、分工發射、人工回報綁定**，不擴充新版圖、模型自動互傳、雲端記憶或外部 API。規章描述應有行為；不代表遠端能力已部署。

## 一、核心目的

使用者在主腦中提出一個共同問題，生成**同一專案下三份分工不同、識別碼各自獨立**的指令。發射器是任務編排與交接入口，不是第四位判斷者；GPT①、GPT②、BOT③ 不是同一回覆的三個名稱。

> 起點：使用者目標 → 三方個別指令 → **人工複製／分享** → 人工貼回回報 → 以原指令 ID 比對 → 待驗證／退回／留存。

## 二、分工責任

| 角色 | 主要工作 | 必須說明 | 不可擅自做 |
| --- | --- | --- | --- |
| GPT①｜統籌 | 整理研究問題、假設、目標、成果驗收條件，負責把分歧形成候選方案 | 要解決什麼、依據何在、哪些仍未知 | 宣稱另兩方已驗證、未經使用者批准就覆蓋正式記憶 |
| GPT②｜反證 | 獨立尋找反例、替代解釋、證據缺口與不同條件的結論 | 反對哪個主張、為何、證據與不確定性 | 為了和 GPT① 一致而隱藏分歧；把推論說成事實 |
| BOT③｜條件測試 | 設計或在授權條件下執行重現、邊界與條件變化測試 | 測試輸入、條件、結果、限制、未完成原因 | 沒有工具／權限時聲稱已實測；未授權寫入或部署 |

**發射順序**：重要問題先讓 GPT① 定義任務、GPT② 獨立反證、BOT③ 依明確條件測試。V1 允許同批一次生成三份指令，但**每份各自交接、各自回收**；無法保證真正 AI 會彼此對話。

## 三、發射前必要欄位

| 欄位 | 用途 |
| --- | --- |
| Project ID | 綁定所屬專案，避免不同討論混入 |
| Relay Batch ID | 同一個問題的交接批次唯一識別 |
| Command ID | 每個角色自己的原指令：`Batch ID:GPT1/GPT2/BOT3` |
| 任務名稱與共同目標 | 所有人理解同一問題，但責任不同 |
| 必要背景 | 只提供經允許分享的材料；未知明確標記 |
| 完成條件 | 各角色要交什麼，如何判定工作做完 |
| 停止／升級條件 | 何時停止指定任務、如何回報或請求決策 |
| 指定角色與來源標記 | 說明資料是誰手動提供、哪些身分未驗證 |

資料缺漏時拒絕建立交接批次。發射器只產生人工交接指令；不能用「發射成功」代表對方收件。

## 四、發射與狀態變更規則

1. **prepared／待交接**：已建立指令，尚無送達證據。
2. **manual_handoff／已人工複製或分享**：只證明本機交接動作，不表示對方已收到。
3. **reported_unverified／已記錄回報、待查核**：手動回貼內容已綁原指令 ID，作者身分與事實仍未驗證。
4. **rejected／已拒絕**：必須立即顯示拒絕原因、影響及下一步；保留先前內容及識別碼。
5. **paused／已暫停追蹤**：只停止被選定角色的**本機交接操作**，保留資料，其他角色、整體專案對話不受阻斷；不表示能遠端撤銷已經發出的指令。

規章上的「開始／停止」與真的遠端 API 執行狀態分開記錄。V1 沒有獲得服務端收件回執，不得自動新增「AI 已收到」「AI 已完成」等確定狀態。

## 五、回報、拒絕與修正

- 每筆回報都應帶**原 Command ID、角色、聲稱來源、回報內容、時間、證據／反證與未解決事項**。只有命令 ID 與對象一致，才允許綁定。
- 不准用 GPT② 的回報填入 GPT① 指令，也不准無痕覆蓋被拒絕的回報。
- 拒絕時必填：**拒絕理由、受影響事項、可行下一步**。當下提示並保留歷史；提醒收起不等於問題已解決。
- 修正方向應建立新候選或新工作指令，標註原拒絕 ID；不要用重新命名把拒絕紀錄清空。
- 系統不以三方多數表決宣告事實。即使三方意見一致，也只能交給後續證據審查或人工審批。

## 六、記憶、私隱與權限

- 交接批次僅在目前頁面工作狀態中保存；關閉頁面前應**明確匯出 JSON 並確認檔案已儲存**，因為現有三方中樞不會自動保存到中央雲端。
- 記憶包、專案治理匯入採候選制。只有使用者在**已解鎖的本機加密記憶庫**中核准，才能進入該庫的正式版本；核准仍不代表外部世界已驗證為真。
- 不要把私人記憶、密碼、API 金鑰或未獲授權資料放進公開 GitHub 頁面、Issue 或未授權交接對象。
- 所有新狀態、接口、圖像設定、未啟用版塊等屬後續批次需求，本規章不把它們視為本階段「發射分工」的必須依賴。

## 七、單批驗收標準（V1 的完成線）

| 驗收項 | 通過條件 |
| --- | --- |
| 三方生成 | 同專案建立 GPT①／GPT②／BOT③ 三份指令，原 ID 唯一且職責不同 |
| 指令獨立發射 | 一方複製指令，不自動改變其他兩方的發射狀態 |
| 回報關聯 | 只接納符合指定角色與原指令 ID 的手動回報 |
| 拒絕提醒 | 拒絕時即時呈現原因、影響、下一步，保留先前紀錄 |
| 暫停與繼續 | 暫停指定工作不清除進度；對話與其他角色可繼續 |
| 進度交接 | 可以下載完整批次與可供專案治理審核的交接資料 |
| 誠實狀態 | 不得把複製／下載標為「已送達」，不把人工貼回當成身分已驗證 |
| 避免越界 | 不需要完成即時群聊、API、世界模型、動態路徑或企業部署 |

**最小操作演練**：建立一個不含個資的測試專案 → 生成三份不同指令 → 只發射 GPT① → 手動貼回一筆對應回報 → 對 GPT② 登記拒絕理由、影響與下一步 → 暫停 BOT③ → 匯出完整批次 → 重新載入確認進度／拒絕保留。

## 八、維護與變更制度

本版以現有 `relay-hub.html`、`tcvl-relay-core.js` 與原 `launcher.html` 的人工交接功能為依據。每個新增需求先列入候選，不得因一般聊天內容變動，就自動打斷或覆蓋正在工作的交接批次。若改變既有規章，須標明：修改原因、受影響欄位、舊版與新版差異、預期測試、是否需要使用者批准。

> **本規章是「可供審核的開發版」，尚未獲使用者明確最終核准，也尚未通過真正手機與瀏覽器端的整合驗收。**
